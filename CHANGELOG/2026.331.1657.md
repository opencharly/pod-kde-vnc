### Spike — the behavioural release this PR carries

`pod-kde-nested` `v2026.331.1638` is a behavioural fix: the nested Plasma session used to lock itself
after Plasma's 5-minute idle `Timeout`, so the streamed desktop became a greeter nobody could type
into. R12 applies, and the spike was run in the leaf's own repo on disposable pods, with no restarts
(a restart re-spawns the greeter with `--immediateLock` and confounds every reading):

```
control, no kscreenlockerrc:   uptime 0:35:42  ->  greeters=1, ScreenSaver.GetActive=true
                               uptime 1:07:37  ->  still locked
with the policy written into the image, same pod, no restart:
                               uptime 0:08:04  ->  greeters=0, ScreenSaver.GetActive=false
```

Two candidate policies were measured before the winner shipped: `Autolock=false` + `Timeout=0` alone
did **not** stop the lock; `Lock=false` (`Daemon/Lock` is the master switch) is what does. The
instrument is `pgrep -c kscreenlocker_[g]reet` plus `org.freedesktop.ScreenSaver.GetActive` over the
pod's session bus, and the leaf's bed `check-kde-nested-locked` re-proves it on a fresh disposable pod:

```
$ charly check run check-kde-nested-locked        (opencharly/pod-kde-nested, tag v2026.331.1638)
[image-build] PASS after 8m12s
[check-live]  PASS after 7m16s      42 steps: 40 passed, 0 failed, 2 skipped
PASS (steps=16, skipped_checks=14)
```

**What this PR's own bed does NOT prove, stated plainly:** `check-kde-vnc-pod` proves the session runs
from the new leaves; it does not re-run the idle-window boundary, because the boundary's instrument now
lives in the leaf (`check-kde-nested-locked`, pasted above) and running two 8-minute idle beds for one
pin advance would be the same proof twice. The consumer pod that adds Chrome, `pod-kde-vnc-cdp`, carries
the end-to-end version of this claim in its own bed and is tracked as the filed issue below.
